# muonium-common 共享层规范

> 继承仓库根 `AGENTS.md`。适用：本目录 Java/Kotlin 源码、资源及测试。核对：2026-11-11。

## 1. 模块定位

本目录是七棵版本树、十四个加载器目标的**同一份编译输入**，没有独立 Gradle 构建。

| 源根 | 用途 | 编译/执行宿主 |
| --- | --- | --- |
| `src/main/java/` | 版本中立 Java 主体 | 七树的两个加载器 |
| `src/main/kotlin/` | 版本中立 Kotlin 增量代码 | 七树的两个加载器 |
| `src/main/resources/` | 共享字体/图形/配置模板等资源 | 七树的两个加载器 |
| `src/test/java/` | 共用 JUnit/静态守卫 | 七树 Fabric 子工程 |
| `src/test/kotlin/` | 共用 Kotlin 测试 | 七树 Fabric 子工程 |

Kotlin 根可按需创建；不要用空业务类占目录。Java/资源由各 loader `build.gradle` 挂载，Kotlin 由仓库根 `gradle/kotlin-support.gradle` 接线。

“共享”不是“所有代码都不许使用 MC”：已验证七树/双加载器一致的官方 API 可沿用。真正禁止的是加载器耦合、版本专属 API 和破坏最低车道的语言/库调用。需要接触易变 MC API 时优先使用现有 compat/宿主桥。

## 共享兼容性的判定（强制）

- 遵守根规范「API 与版本事实」：共享根被十四个目标挂载，**不等于十四个目标的 MC/加载器 API 相同**。同一棵树的 Fabric 与 Forge/NeoForge 也必须分别核实。
- 只有对实际受影响组合核实了存在性、签名、访问条件和所需行为的调用，才能认定为可共享；不能靠官方名相同、代码相同或一个目标编译通过做结论。
- **统一的是项目自己定义的业务契约，不是外部 API**。各树 compat、各加载器宿主桥可以且应当采用不同实现；不得为了表面同文强行调用目标不存在的方法。
- Java/Kotlin 最低语言基线只约束语言和 JDK/标准库使用范围，不证明 Minecraft API 或 loader 行为兼容；第三方库也以各组合实际解析版本为准。
- 共享调用变化逐组合检查适配端。能力不等价时明确能力边界及经确认的降级路径；未确认就标为未确认，不用空实现、反射猜方法或吞异常伪造支持。
- 验收记录按「MC 精确版本 × 加载器/依赖版本」区分声明核实、编译、测试和实测；不得用 Fabric 的结果替 Forge/NeoForge 背书。

## 2. 依赖与语言底线

- 禁止 `net.fabricmc.*`、`net.neoforged.*`、`net.minecraftforge.*`、`cpw.mods.*` 的直接引用、Kotlin alias 或反射绕行；加载器注册留外壳。
- 共享 Java 按 **Java 17** 的语法和 JDK API 上限写；不能在 26.3 用 Java 25 编译通过后就算完成。
- 共享 Kotlin 按**语言/API 1.8、stdlib 1.8.22、Java 17 API**上限写。实际编译器版本不等于可用语言/API 基线。
- 不把 Kotlin runtime、FLK/KFF adapter 或新的 kotlinx API 当作共享业务默认可用依赖；runtime 仍由前置提供，不嵌第二份 `kotlin.*`。
- Java/Kotlin 双向调用保持既有 Java 接口；需要静态入口时显式设计 `@JvmStatic` / Java 门面。Lombok `@UtilityClass` 的隐式静态方法不能假定同轮 Kotlin 可见；用小型显式 static Java 桥，不重写旧工具类。
- 不因新语言接入改线程模型、引入协程/序列化框架或批量迁移既有 Java/Mixin。

## 3. 版本差异的正确放法

新增能力先区分三部分：

1. **业务语义/算法/纯数据**：放本目录，只保留一份。
2. **MC/窗口/渲染 API 适配**：放七树各自的 `compat/`，提供相同共享调用契约。
3. **加载器事件/生命周期/网络注册**：放 `<树>/<加载器>/src/main/`。

契约要求：共享调用的类名、方法名、参数、返回值、单位、线程、生命周期和降级语义保持一致；接口只暴露可跨车道理解的类型，不从新版本向共享层泄漏独有 MC 类型。必要时用已有中立 DTO/接口承接。

- 七树适配可以内部不同，但不能“方法同名、行为相反”。缺能力要明确无操作/失败返回或降级，不伪造成功。
- 不能为了一个版本差异回搬整个共享文件，也不能在共享层堆版本号分支或探测 loader。
- 现有树内留守类仍按守卫维护；收敛历史副本须单独评估其 API 与行为差异，不机械合并。
- Mixin 留树内并校验注入阶段与描述符；源码碰巧相同不构成共享理由。

## 4. 新文件与归属变更

### 4.1 日常新增版本中立文件

直接在本目录合适源根创建文件和共用测试。检查所有挂载根无同名路径/类，遵守最低车道，然后跑七树测试及所需双加载器构建。**不需要先在七树复制七份，再运行迁移器。**

### 4.2 新增树内留守类

先说明不能共享的具体 API/生命周期原因，并尝试将差异缩成 compat 方法。确需新文件时：

- 在 `SharedLayoutStaticTest` 对应 `REQUIRED_MAIN_JAVA` / `OPTIONAL_MAIN_JAVA`、测试表或 Kotlin 留守表登记。
- REQUIRED 表示每树必有；OPTIONAL 表示允许部分树存在，不是允许七树任意丢实现。
- 在 `tools/share-trees.py` 的 `REASONS` 记录原因；此工具当前被忽略，交付时说明本机改动是否纳入版本控制。
- 在对应版本/子系统规范写清存在范围、行为差异和验收；不要把历史迁移清单当实时登记系统。
- 修改守卫的理由必须是架构边界变化，不能只是“测试红了”。

### 4.3 将既有树内类收敛进共享

逐树比较代码与语义，先拆出 compat 差异，再移动成一份；删除各树副本，调整守卫和归属理由，验证所有车道。文件归属修改与行为重构尽量分开，不能留下双份定义。

## 5. 迁移工具不是日常检查器

`tools/share-trees.py` 是历史跨树去重迁移器。当前仓库已迁移完成：

| 子命令/文件 | 当前含义与限制 |
| --- | --- |
| `classify` | 扫迁移前各树并写 `.scratch/share-snapshot.json`；不是只读命令，当前已有共享主体时会主动拒绝 |
| `apply --confirm` | 按历史底片搬运/删除文件并生成清单；不是日常新增文件或刷新清单入口，不运行来修测试 |
| `verify` | 对照本机历史底片检查迁移集合；会受后来新增文件/旧底片影响，不是当前布局验收的替代品 |
| `wire` | 会写各 loader 构建文件，依赖历史文本锚点；Kotlin 仅核对共享脚本接入，不是无副作用检查 |
| `SHARE-MANIFEST.md` | 历史迁移生成记录；统计与“存在树”可能过时，不手改统计、不宣称它完整反映现状 |

**日常权威**是实际 sourceSets、当前文件布局与 `src/test/java/com/muoniumplayer/SharedLayoutStaticTest.java`。不要重跑迁移或改写 `.scratch` 底片来掩盖归属错误。

## 6. 资源、线程和生命周期

- 资源按原始字节读写/比较/复制；禁止把 png/ttf/dll 等当 UTF-8 文本归一化。
- 共享、本树与外壳资源不能靠覆盖顺序解决冲突；版本专有资源留本树，loader 元数据留外壳。
- 共用测试使用 `ProjectPaths` 定位共享根/本树根；不硬编码工作目录、盘符或某树的 build 输出。
- 新增扫描守卫同时考虑 `.java` 与 `.kt`；Kotlin raw string/嵌套注释不能套 Java 剥注释正则。
- 音频、网络、渲染的线程所有权和异步发布沿用子系统约定；缓存/原生资源修改必须定义失效与释放路径。
- 对外字段/反射方法、持久化 key/default、缓存版本与协议字段按契约维护，不做无兼容迁移的随手改名。

## 7. 验收与交付

从仓库根执行：

```powershell
# 七树共用 JUnit，包含布局/加载器符号/Kotlin 接线等守卫
.\tools\build-all.ps1 -Task ':fabric:test' -KeepOldJars

# 共享生产代码/依赖变更：完整双加载器构建
.\tools\build-all.ps1

# Kotlin 构建接线变更额外验证
python -I tools\kotlin-support-tests.py
```

`test` 不能覆盖另一 loader 编译，`build` 不能证明游戏内渲染、音频或 Mixin 成功。按根规范补运行验证，并逐项列明通过、失败和未运行范围。纯 Markdown 改动只需文档一致性校验。
